## Детали по открытым пунктам

### Шеринг подборок (фаза 4)

Подборки локальны в IndexedDB с autoIncrement `id` — расшарить `id` бессмысленно. Но база песен общая (один `songs.json`), поэтому подборка = `{name, [(songNumber, variantIndex), …]}`.

**Версионирование.** Поле `version` (целое, монотонное) в корне `songs.json`. Файл собирает `songs-data/parse.js` (`const result = { songs, sections }`) — правка идёт туда; `scripts/parseTxt.js` — LEGACY, на сборку не влияет и не трогается. Источник значения — ручной счётчик в `songs-data/version.txt` (одно целое число), `parse.js` читает его и кладёт в корень (фолбэк `0`, если файла нет). Инкремент вручную при значимых изменениях данных: добавили или переразбили песни, поменяли варианты. Требование инкрементить зафиксировать в CLAUDE.md рядом с описанием `songs-data/`, иначе забудется. `songsVersion` сохраняется в настройках при `fetchSongs` — там же, где уже пишется `songsEtag`.

В payload кладём `v` — версию базы у того, кто делится.

| У получателя версия | Действие |
|---|---|
| **Меньше**, чем в payload | База устарела → «Обновите базу данных» + кнопка; после обновления повторить импорт. |
| **Больше или равна** | Импорт. Валидация: песня не найдена → пропустить с предупреждением; `variantIndex` вне диапазона вариантов → прижать к 0 с пометкой. |

Случай «у отправителя база ниже, чем у получателя» безопасен: подборка ссылается на номера и индексы вариантов, а не на контент, а номера стабильны. Риск — изменившиеся варианты: падаем на variant 0 с мягким предупреждением «подборка из более старой версии базы, проверьте варианты».

**Формат кодирования** (обоснование — Приложение А). Payload — компактная строка, а не JSON: маркер формата, имя, версия базы, список номеров через запятую, вариант через точку у тех песен, где он не нулевой.

```
2
Молодёжное служение — воскресенье
3
14,102.1,340,507,1120.2
```

Первая строка — маркер формата (`1` = без сжатия, `2` = gzip): он позволит добавить сжатие позже, не ломая уже разосланные ссылки. Итоговая строка — base64url без сжатия. Сжатие выигрывает только на больших подборках, а на маленьких проигрывает чистому base64url из-за заголовка gzip; lz-string и gzip по размеру почти равны, но lz-string — новая зависимость. Без сжатия в 2000 символов URL укладывается 304 песни — с запасом для любой реальной подборки.

**Ограничение длины — деградация, а не лимит на подборку.** Ограничивать саму подборку не нужно: это локальная сущность, лимит бил бы и по тем, кто ничего не шарит. Проверяется длина итоговой строки (число песен — плохой прокси: номера бывают 1–4 знака, имя подборки тоже влияет). Порог — 2000 символов на весь URL, консервативный: fragment на сервер не уходит и браузеры держат гораздо больше, но ссылку могут обрезать мессенджеры и превью-парсеры.

| Ступень | Что делаем | Влезает в 2000 симв. |
|---|---|---|
| 1 | compact + base64url (маркер `1`) | 304 песни |
| 2 | Строка превысила порог → gzip через `CompressionStream` (маркер `2`) | 660 песен |
| 3 | И это превышено → предложить экспорт файлом (механизм из 2.3) | без лимита |

Ступень 2 требует `CompressionStream` (Chrome 80+, Safari 16.4+); если API недоступен — сразу ступень 3.

**Ограничения по решению:**
- Делиться только обычными подборками, «Избранным» — нет.
- При импорте предлагать слить с существующей по имени.
- Маршрут импорта — `/collections/import#<data>`: fragment не уходит на сервер, серверного лимита длины нет.
- **Вся фаза 4, включая страницу импорта, — за devMode.** Следствие принимаем осознанно: ссылка сработает только у получателя с включённым dev-режимом, то есть на этапе обкатки шеринг живёт между своими устройствами. Выход из dev-режима — отдельное решение после обкатки; до него внешним людям ссылки не рассылаем, иначе они увидят заглушку.

### Что даёт гейт dev-режима

Приложение статическое (`ssr: false`), поэтому `npm run generate` всё равно выложит HTML для `/songs` и `/collections/import` — они останутся доступны по прямому URL. Гейт скрывает **вход** (ссылку в меню, кнопку), а не закрывает маршрут. Для «не маячит обычному пользователю» этого достаточно, но рассчитывать на гейт как на защиту нельзя. На экспериментальных страницах при `devMode=false` показывать заглушку с объяснением, а не пустоту — иначе случайный переход выглядит как поломка.

Гейтятся: список песен (фаза 3), шеринг целиком (фаза 4), аккорды (фаза 5). Общедоступны: «О приложении», поворот, синглтон поиска, сохранность данных.

## Приложение А. Замеры кодирования подборки

Замер от 2026-08-03 на реальной базе (1565 песен). Подборки — случайные номера по всему сборнику (важно: номера с постоянным шагом сжимаются нереалистично хорошо и завышают выигрыш сжатия). Имя подборки — «Молодёжное служение — воскресенье» (33 символа, кириллица — в UTF-8 занимает вдвое больше байт, чем латиница). В таблице — длина **итогового URL** с production-префиксом `https://…/nuxt-songs-app/collections/import#` (61 символ).

| Песен | payload, байт (JSON / compact) | URL base64url (JSON) | URL base64url (compact) | URL gzip (compact) | URL lz-string (compact) |
|---|---|---|---|---|---|
| 5 | 100 / 57 | 236 | **179** | 199 | 173 |
| 20 | 224 / 125 | 401 | **269** | 255 | 235 |
| 50 | 481 / 272 | 744 | **465** | 343 | 334 |
| 150 | 1307 / 726 | 1845 | 1071 | **615** | 648 |
| 300 | 2557 / 1418 | 3512 | 1993 | **1024** | 1080 |
| 500 | 4211 / 2330 | 5717 | 3209 | **1564** | 1625 |

Сколько песен влезает в 2000 символов URL:

| payload | base64url | gzip | lz-string |
|---|---|---|---|
| JSON | 164 | 562 | 529 |
| compact | **304** | **660** | 630 |

Время кодирования (150 песен, среднее по 500 вызовам): base64url 0.002 мс, gzip 0.013 мс, lz-string 0.053 мс — все варианты неощутимы, время не является критерием выбора.

**Выводы:**
1. **Формат payload важнее компрессора:** переход с JSON на компактную строку срезает ~40% ещё до всякого сжатия.
2. **На маленьких подборках сжатие вредит:** при 5 песнях gzip даёт URL длиннее, чем чистый base64url (199 против 179) — 18-байтовый заголовок gzip не отбивается. А реальные подборки — это единицы-десятки песен.
3. **gzip и lz-string эквивалентны по размеру** (разница 5–8% в пользу gzip), поэтому новая зависимость `lz-string` не оправдана: если сжатие понадобится, встроенный `CompressionStream` даёт то же самое бесплатно.
4. Отсюда решение фазы 4: compact + base64url без сжатия, маркер формата для будущего gzip, деградация до экспорта файлом вместо лимита на размер подборки.

Скрипт замера не хранится в репозитории (разовый). Воспроизводится по описанию выше; для повторения важно брать номера случайно и считать длину именно URL, а не payload.

## Приложение Б. Ловушки в данных (проверено по коду)

- **Номер песни называется по-разному на разных слоях.** В `songs.json` поле — `n` (`songs-data/parse.js`), в IndexedDB — `number`: преобразование делает `composables/useIndexDB.js` (`number: Number(song.n)`). Код, читающий сырой `songs.json` (парсер, скрипты, кодирование подборок при экспорте), должен брать `n`; код, работающий с IndexedDB, — `number`. Молчаливый источник NaN.
- **Внутри `variants[].body` тоже есть `n`** — это номер куплета или припева, не номер песни.
- **Ремарка исполнителю бывает и в круглых скобках.** Квадратные скобки поиск не индексирует (`stripRemarks`, пункт 6.2), но, например, в `1414:33` указание записано как `(мелодия 2-ой части куплета)` — оно в индексе остаётся. Расширить чистку на круглые скобки нельзя: там же лежат слова песни (подголоски в `0662`, вторые голоса в `1289`). Если случай станет массовым, лечится приведением таких ремарок к квадратным скобкам в данных, а не правкой поиска.
- **Маркер репризы попадает в индекс термом.** `cleanText` снимает слеши, но «2р.» из `/.../ 2р.` остаётся: в документе 1158 индексируется «…молодых и старых 2р От Пилата…». На выдачу это почти не влияет (запросов вида «2р» не бывает), но при разборе странного ранжирования такой терм стоит помнить.
- **`ssr: false`** в `nuxt.config.js`. Для новых страниц это упрощает работу с IndexedDB: серверного рендера нет. Но и статику генерирует для всех маршрутов — см. «Что даёт гейт dev-режима».
- **Версия БД — 7**, единственный источник — `lib/dbSchema.js` (`DB_VERSION`, `createSchema`); шаги миграций — `lib/dbMigrations.js`. При изменении схемы (5.2) править только их и покрывать в `lib/dbMigrations.test.js`, где апгрейд прогоняется с каждой из версий 1–5.
