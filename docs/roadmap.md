**Дата составления:** 2026-07-29
**Уточнён:** 2026-08-03 — сверка с кодом, замеры кодирования подборок
**Статус:** согласован, готов к реализации

## Исходные замечания

1. Долго открывается попап поиска при клике по номеру песни на странице песни.
2. Страница списка песен с сортировкой по номеру / по алфавиту / группировкой по разделам.
3. Не работает поворот на бок в установленном PWA.
4. Делиться подборками через ссылку.
5. Страница инструкции.

## Решения по пунктам

### 1. Попап поиска — синглтон индекса

**Причина:** попап обёрнут в `v-if` + `<Transition>`, внутри `<SongSearchInput>`, который при каждом открытии монтируется заново и в `onMounted` строит индекс Lunr + exact-индекс по 1565 песен (`composables/useSongSearch.js:10`, `components/SongSearchInput.vue:65`). На главной индекс строится один раз — поэтому там быстро.

**Решение:** вынести индексы `useSongSearch` на уровень модуля (синглтон); `buildIndex` — no-op, если индекс уже построен. Строить один раз за сессию при первом доступе к `allSongs`. Попап на странице песни открывается мгновенно.

**Важно — синглтон только для индексов.** `useSongSearch()` возвращает не только `searchIndex`/`exactIndex`, но и `searchQuery`/`searchResults` (`composables/useSongSearch.js:7-8`). Сейчас у поля на главной и у попапа на странице песни они независимы. Если вынести на модуль **весь** state, два инстанса начнут делить запрос и выдачу: `clear()` в одном месте затрёт другое, ввод в попапе «протечёт» на главную. Синглтоном становятся только `searchIndex` и `exactIndex`; `searchQuery`/`searchResults` остаются локальными для каждого инстанса.

**Вторая половина лага — загрузка песен из IndexedDB.** `pages/song/[number].vue:248` вызывает `getAllSongs()` (1565 записей с полным текстом) при **каждом** переходе на песню, независимо от индекса. Синглтон индекса эту стоимость не убирает. Нужен модульный кэш `allSongs` (грузим один раз за сессию, инвалидируем после обновления базы через `fetchSongs`). Без этого выигрыш будет частичным.

**Мелочь по ходу:** `getSongTitle`/`getVariantLabel` (`components/SongSearchInput.vue:102-111`) делают линейный `find` по 1565 песням на каждый результат выдачи. При кэшировании песен заодно построить `Map` по номеру.

**Уточнено:** лаг при каждом открытии → синглтон индекса + кэш песен решают.

### 2. Страница списка песен

Новой страницы нет; данные есть — `songs.json` содержит `sections` (54 раздела с `song_ns`) и `title` у каждой песни.

**Решение:** маршрут `/songs` с тремя режимами:
- **По номеру** — плоский список 1…1565.
- **По алфавиту** — группировка по первой букве названия. Латиницы/цифр сейчас нет, но группу «#» держим на будущее.
- **По разделам** — группы по `sections[].title` + песни из `song_ns`.

Производительность: 1565 элементов → сворачиваемые секции (по умолчанию свёрнуты, кроме первой). Варианты (а/б) не показываем. В список встроить кнопку-иконку открытия попапа с `SongSearchInput` (как на странице песни) — переиспользуем синглтон-индекс из п.1. Поиск остаётся и на главной.

**Уточнено:**
- Вход — «Все песни» в боковом меню (только при `devMode`).
- Варианты в списке пока не отображаем.

### 3. Поворот на бок

**Причина:** в манифесте PWA `orientation: 'portrait'` (`nuxt.config.js:40`) — блокирует ландшафт в установленном PWA. В браузере поворот работает (манифест не влияет).

**Решение:** `orientation: 'portrait'` → `'any'`. После — обязательная визуальная проверка ландшафта через Playwright-скриншот (по правилам редизайна): узкая колонка текста, навбар.

**Ожидание по срокам применения:** установленный PWA перечитывает манифест не мгновенно — Chrome на Android обновляет закреплённые параметры с задержкой (при следующих запусках, иногда только после переустановки приложения). Значит после деплоя фикс может «не сработать» на устройстве, где приложение уже стоит. Проверять так: сначала браузер и свежая установка (там эффект сразу), и только потом ждать подхвата на старой установке. Иначе легко принять задержку манифеста за нерабочий фикс.

**Уточнено:** баг именно в установленном PWA; вёрстку в ландшафте ещё не проверяли (не поворачивалось).

### 4. Шеринг подборок через ссылку

Подборки локальны в IndexedDB с autoIncrement `id` — расшарить `id` бессмысленно. Но база песен общая (один `songs.json`), поэтому подборка = `{name, [(songNumber, variantIndex), …]}`.

**Версионирование:** добавить поле `version` (целое, монотонное) в `songs.json`. **Собирает файл `songs-data/parse.js:217`** (`const result = { songs, sections }`) — правка идёт туда; `scripts/parseTxt.js` — LEGACY, на сборку не влияет и не трогается.

Источник значения — **ручной счётчик** в отдельном файле `songs-data/version.txt` (одно целое число). `parse.js` читает его и кладёт в корень `songs.json` (фолбэк `0`, если файла нет). Инкремент вручную при значимых изменениях данных — добавили/переразбили песни, поменяли варианты. Требование инкрементить зафиксировать в CLAUDE.md рядом с описанием `songs-data/`, иначе забудется. `songsVersion` сохраняется в настройках при `fetchSongs` — там же, где уже пишется `songsEtag`.

В payload шеринга класть `v` = версия базы у того, кто делится.

Логика при импорте у получателя:

| У получателя версия | Действие |
|---|---|
| **Меньше**, чем в payload | База устарела → «Обновите базу данных» + кнопка; после обновления повторить импорт. |
| **Больше или равна** | Импорт. Валидация: песня не найдена → пропустить с предупреждением; `variantIndex` вне диапазона вариантов → прижать к 0 с пометкой. |

Случай «у того, кто делится, база ниже, чем у получателя» — безопасен: подборка ссылается только на номера + индексы вариантов, а не на контент; номера стабильны. Риск — изменившиеся варианты → падаем на variant 0 с мягким предупреждением «подборка из более старой версии базы, проверьте варианты».

**Решение:**
- Общий модуль кодирования подборки → строка. Переиспользуется в экспорте (п.7).
- Кнопка «Поделиться» на странице подборки: `navigator.share` + копирование ссылки. Только обычные подборки.
- Маршрут `/collections/import#<data>` (fragment — не уходит на сервер, нет лимита длины на стороне сервера): просмотр (read-only) + «Сохранить в мои подборки» с предложением слить с существующей по имени.

#### Формат кодирования (обоснование — Приложение А)

Payload — **компактная строка**, а не JSON: имя, версия базы, список номеров через запятую, вариант через точку у тех песен, где он не нулевой.

```
2
Молодёжное служение — воскресенье
3
14,102.1,340,507,1120.2
```
Первая строка — **маркер формата** (`1` = без сжатия, `2` = gzip). Он позволит позже добавить сжатие, не ломая уже разосланные ссылки. Дальше: имя, версия базы, номера.

Итоговая строка — base64url, **без сжатия**. Обоснование: сжатие даёт выигрыш только на больших подборках, а на маленьких (5 песен) проигрывает чистому base64url из-за заголовка gzip; lz-string и gzip по размеру почти равны, но lz-string — новая зависимость. Без сжатия в 2000 символов URL укладывается 304 песни — с запасом для любой реальной подборки.

#### Ограничение длины ссылки — деградация, а не лимит на подборку

Ограничивать саму подборку не нужно: это локальная сущность, лимит бил бы и по тем, кто ничего не шарит. Проверяется **длина итоговой строки** (число песен — плохой прокси: номера бывают 1–4 знака, имя подборки тоже влияет). Порог — 2000 символов на весь URL, консервативный: fragment на сервер не уходит и браузеры держат гораздо больше, но ссылку могут обрезать мессенджеры и превью-парсеры.

| Ступень | Что делаем | Влезает в 2000 симв. |
|---|---|---|
| 1 | compact + base64url (маркер `1`) | 304 песни |
| 2 | Строка превысила порог → gzip через `CompressionStream` (маркер `2`) | 660 песен |
| 3 | И это превышено → предложить экспорт файлом (механизм из п.7.3) | без лимита |

Ступень 2 требует `CompressionStream` (Chrome 80+, Safari 16.4+); если API недоступен — сразу ступень 3. Практически ступень 1 покрывает всё, ступени 2–3 — страховка, поэтому реализуются после 4.3, когда основной путь работает.

**Уточнено:**
- Делиться только обычными подборками («Избранное» — нет).
- При импорте — предлагать слить с существующей по имени.
- Версионирование — как выше, ручной счётчик в `songs-data/version.txt`.
- Кодирование — компактная строка + base64url без сжатия, с маркером формата.
- **Вся Фаза 4 (включая страницу импорта) — за devMode.** Следствие принимаем осознанно: ссылка сработает только у получателя с включённым dev-режимом, то есть на этапе обкатки шеринг живёт между своими устройствами. Выход из dev-режима для этой фазы — отдельное решение после обкатки; до него внешним людям ссылки не рассылаем, иначе они увидят пустую страницу.

### 5. Страница инструкции + «О приложении» (объединяем)

Маршрут `/about`. Короткая шпаргалка по экранам + блок «О приложении» (версия/коммит/дата сборки из `appConfig`: `appVersion`, `appCommit`, `appBuildDate`). Вход — из бокового меню внизу, рядом с «Настройки».

На этой же странице — блок диагностики (см. п.7) и активация dev-режима (см. п.6).

### 6. Режим разработчика

Поле `settings.devMode` (boolean, персистентно). Активация — 7 тапов по версии приложения на странице «О приложении» (Android-style, не маячит обычным пользователям). В `settings.vue` появляется секция «Экспериментальные функции» при `devMode=true`.

**Гейтить за dev-режимом:** все новые фичи (список песен п.2, шеринг п.4 целиком) + скрытые сейчас (аккорды). «О приложении», поворот, синглтон поиска, сохранность данных — общедоступны.

**Что именно даёт гейт.** Приложение статическое (`ssr: false`), поэтому `npm run generate` всё равно выложит HTML для `/songs` и `/collections/import` — они останутся доступны по прямому URL. Гейт скрывает **вход** (ссылку в меню, кнопку), а не закрывает маршрут. Это нормально для «не маячит обычному пользователю», но нельзя рассчитывать на него как на защиту. На самих экспериментальных страницах при `devMode=false` показывать заглушку с объяснением, а не пустоту — иначе случайный переход выглядит как поломка.

**Уточнено:**
- Активация тапом по версии на странице «О приложении».
- Все новые фичи проводим через dev-режим.
- `settings.devMode` добавляется тем же способом, что остальные поля стора — `useStorage('devMode', false)` в `stores/settings.js` + действие `setDevMode`.

### 7. Потеря подборок — сохранность данных

**Симптомы:** пропали сами записи коллекций (с названиями), часть осталась, базу не обновляли, кэш не чистили, доступа к устройству нет.

**Что не подходит:** миграции не удаляют записи из `collections` (только `songCollections.clear()` в v2→v3/v3→v4) → не объясняют потерю имён; `deleteCollection` требует подтверждения на каждую → случайно потерять «часть» малореально.

**Наиболее вероятная причина:** eviction хранилища браузером. IndexedDB без `navigator.storage.persist()` помечен как best-effort — браузер/ОС могут освободить его при нехватке места; на Android известны случаи частичной потери. В коде `navigator.storage.persist()` не вызывается.

**Отдельный подтверждённый риск в миграциях** (не объясняет потерю имён, но способен уронить базу целиком). Миграция v3→v4 (`plugins/indexedDB.client.js:80-96`) создаёт **уникальный** индекс `collectionId_songNumber_variantIndex` и одновременно переписывает все связи с `variantIndex: 0`. Если у пользователя одна и та же песня была добавлена в подборку в двух вариантах (а ключ до v4 включал `variantLabel`, что это разрешало), два разных ключа схлопываются в один → `ConstraintError` → **abort транзакции апгрейда**. Тогда `request.onerror` (строка 162) реджектит промис, плагин падает целиком, `nuxtApp.provide('indexedDB', db)` не выполняется — и приложение выглядит так, будто данных нет вообще. Тот же сценарий у v2→v3 (строка 57). Это нужно устранить в 2.4 и обязательно показывать в диагностике (2.5): сейчас такая ошибка уходит только в консоль, до которой нет доступа.

**Вывод:** без устройства точную причину не установить → работаем на профилактику + диагностику.

**А. Профилактика:**
1. `navigator.storage.persist()` при первом взаимодействии.
2. Авто-бэкап подборок в localStorage при каждом изменении (данные крошечные: имена + связи).
3. Ручной экспорт/импорт JSON в настройках (+ «восстановить из бэкапа», если при старте коллекции пусты, а в localStorage есть бэкап). Переиспользует кодирование из п.4.
4. Харденинг миграций: убрать `clear()` перед повторным `put`, перейти на upsert через курсор; перед созданием уникального индекса дедуплицировать связи, а не полагаться на то, что дублей нет.
5. Не валить плагин при ошибке открытия БД: перехватывать `onerror`/`onblocked`, сохранять текст ошибки в память приложения и показывать его в блоке диагностики. Сейчас единственная ошибка апгрейда обнуляет всё приложение.

**Б. Диагностика на будущее** (доступа к DevTools нет):
6. На странице «О приложении» — блок диагностики: «Подборок: N, Связей: M, Песен: K, Версия БД: V, Persistent: да/нет, последняя ошибка БД: …».

**Уточнено:**
- Пропали сами подборки (с названиями), часть осталась.
- Базу не обновляли, кэш не чистили.
- Доступа к устройству нет — точно причину назвать нельзя.

## Фазы и порядок работ

```
Фаза 0 (dev-режим + /about) ──► Фаза 3, 4, 5 (всё за dev-режимом)
                            └──► 2.5 (блок диагностики на /about)
Фаза 1 (независимо)
Фаза 2 (независимо, кроме 2.5)
Фаза 4 переиспользует кодирование из 2.3
```

Зависимость 0.2 ↔ 2.5 односторонняя: страница `/about` создаётся в 0.2 **без** блока диагностики, блок добавляется в 2.5. Ранняя редакция плана помечала зависимость в обе стороны — это была ошибка, 0.2 ничего от 2.5 не ждёт.

### Фаза 0 — Фундамент
- **0.1.** Dev-режим: `settings.devMode` (`useStorage` + `setDevMode`), активация 7 тапов по версии на `/about`, секция «Экспериментальные функции» в `settings.vue`.
- **0.2.** Страница `/about`: шпаргалка + блок «О приложении» (`appVersion`, `appCommit`, `appBuildDate` из `appConfig` — уже есть в `nuxt.config.js:10-14`). Вход — из бокового меню рядом с «Настройки» (`layouts/default.vue:97-104`).

### Фаза 1 — Быстрые победы
- **1.1.** Синглтон поисковых индексов + модульный кэш `allSongs` (п.1). `searchQuery`/`searchResults` оставить локальными.
- **1.2.** Поворот: `orientation: 'any'` (`nuxt.config.js:40`) + визуальная проверка ландшафта; учесть задержку подхвата манифеста (п.3).

### Фаза 2 — Сохранность данных (п.7)
- **2.1.** `navigator.storage.persist()`.
- **2.2.** Авто-бэкап подборок в localStorage.
- **2.3.** Ручной экспорт/импорт JSON в настройках.
- **2.4.** Харденинг миграций: upsert без `clear`, дедуп связей перед уникальным индексом, устойчивость плагина к ошибке открытия БД (п.7.А.4-5).
- **2.5.** Блок диагностики на `/about` (требует 0.2).

### Фаза 3 — Список песен (п.2), за dev-режимом
- **3.1.** Маршрут `/songs`: по номеру / по алфавиту / по разделам (54 раздела из `sections`, 1565 песен).
- **3.2.** Сворачиваемые секции; варианты не показываем.
- **3.3.** Кнопка попапа поиска в списке (переиспользует синглтон из 1.1).
- **3.4.** Вход «Все песни» в боковом меню при `devMode`; заглушка на `/songs` при `devMode=false`.

### Фаза 4 — Шеринг подборок (п.4), за dev-режимом
- **4.1.** `version` в `songs.json` через `songs-data/parse.js` + `songs-data/version.txt` + `songsVersion` в настройках; отметка в CLAUDE.md про ручной инкремент.
- **4.2.** Общий модуль кодирования подборки: компактный payload + base64url, маркер формата (переиспользуется в 2.3).
- **4.3.** Кнопка «Поделиться» на странице подборки (`navigator.share` + копирование ссылки).
- **4.4.** Маршрут `/collections/import#<data>`: просмотр + «Сохранить» с предложением слить по имени; версионирование по таблице выше.
- **4.5.** Деградация по длине ссылки: gzip при превышении порога, экспорт файлом как последняя ступень (после 4.3, когда основной путь работает).

### Фаза 5 — Аккорды

## Приложение А. Замеры кодирования подборки

Замер от 2026-08-03 на реальной базе (1565 песен). Подборки — случайные номера по всему сборнику (важно: номера с постоянным шагом сжимаются нереалистично хорошо и завышают выигрыш сжатия). Имя подборки — «Молодёжное служение — воскресенье» (33 символа, кириллица — в UTF-8 занимает вдвое больше байт, чем латиница). В таблице — длина **итогового URL** с production-префиксом `https://…/nuxt-songs-app/collections/import#` (61 символ).

| Песен | payload, байт (JSON / compact) | URL base64url (JSON) | URL base64url (compact) | URL gzip (compact) | URL lz-string (compact) |
|---|---|---|---|---|---|
| 5 | 100 / 57 | 236 | **179** | 199 | 173 |
| 20 | 224 / 125 | 401 | **269** | 255 | 235 |
| 50 | 481 / 272 | 744 | **465** | 343 | 334 |
| 150 | 1307 / 726 | 1845 | 1071 | **615** | 648 |
| 300 | 2557 / 1418 | 3512 | 1993 | **1024** | 1080 |
| 500 | 4211 / 2330 | 5717 | 3209 | **1564** | 1625 |

Сколько песен влезает в 2000 символов URL:

| payload | base64url | gzip | lz-string |
|---|---|---|---|
| JSON | 164 | 562 | 529 |
| compact | **304** | **660** | 630 |

Время кодирования (150 песен, среднее по 500 вызовам): base64url 0.002 мс, gzip 0.013 мс, lz-string 0.053 мс — все варианты неощутимы, время не является критерием выбора.

**Выводы:**
1. **Формат payload важнее компрессора:** переход с JSON на компактную строку срезает ~40% ещё до всякого сжатия.
2. **На маленьких подборках сжатие вредит:** при 5 песнях gzip даёт URL длиннее, чем чистый base64url (199 против 179) — 18-байтовый заголовок gzip не отбивается. А реальные подборки — это единицы-десятки песен.
3. **gzip и lz-string эквивалентны по размеру** (разница 5–8% в пользу gzip), поэтому новая зависимость `lz-string` не оправдана: если сжатие когда-то понадобится, встроенный `CompressionStream` даёт то же самое бесплатно.
4. Отсюда решение из п.4: compact + base64url без сжатия, маркер формата для будущего gzip, деградация до экспорта файлом вместо лимита на размер подборки.

Скрипт замера не хранится в репозитории (разовый). Воспроизводится по описанию выше; для повторения важно брать номера случайно и считать длину именно URL, а не payload.

## Приложение Б. Ловушки в данных (проверено по коду)

- **Номер песни называется по-разному на разных слоях.** В `songs.json` поле — `n` (`songs-data/parse.js:168`), в IndexedDB — `number`: преобразование делает `composables/useIndexDB.js:14` (`number: Number(song.n)`). Код, читающий сырой `songs.json` (парсер, скрипты, кодирование подборок при экспорте), должен брать `n`; код, работающий с IndexedDB, — `number`. Молчаливый источник NaN.
- **Внутри `variants[].body` тоже есть `n`** — это номер куплета/припева, не номер песни.
- **`ssr: false`** в `nuxt.config.js`. Для новых страниц это упрощает работу с IndexedDB: серверного рендера нет.
- **Версия БД — 6**, единственный источник — `lib/dbSchema.js` (`DB_VERSION`, `createSchema`). При изменении схемы в 2.4 править только его; миграцию дописывать в `plugins/indexedDB.client.js`. Раньше схема дублировалась в трёх местах — устранено в `4256ad9`.
